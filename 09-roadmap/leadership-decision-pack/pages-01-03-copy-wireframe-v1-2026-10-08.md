## 第 1 页｜决策总览

### 直接可用于投影的标题
**手机 Agent 提升 CPU 的可编程控制、选择性 AI 执行与异构协同价值；目前不支持为 Agent 单独新增 CPU 指令集。**

### 页首结论栏（展示文字）
**2027–2029 年的技术建议：优先建设现有 AArch64/SME2 上的 CPU/LLVM 快速路径、可信工具执行和跨引擎 QoE 管理；对专用硬件保持证据驱动的条件储备。**

### 主图：端侧 Agent 跨层执行框架（占左侧约 58%）
推荐**纵向分层 + 右侧数据反馈弧**，而不是四个缺乏解释的名词框。每层内部采用一行角色定义、两行机制解释：
1. **Agent 与应用任务** — 用户目标可能分成推理、检索和跨应用操作；执行中可能重新规划或被中断。工具返回并不自动代表用户目标已经完成。
2. **Runtime / OS 协调** — 将任务组织为动态阶段及依赖，结合优先级、前台交互和资源压力选择 CPU/GPU/NPU，并负责版本化资源的使用与回收。
3. **CPU / LLVM 与可选 AI 快速执行** — CPU 承担复杂分支、权限/控制和不规则短阶段；MLIR/LLVM 可针对已有 Neon/SVE/SME2 能力选择 lowering、packing 与微内核。不是声称 CPU 适合所有模型阶段。
4. **GPU / NPU 与数据状态** — 高吞吐或适配的模型算子由 GPU/NPU 执行；多引擎之间存在数据布局、共享缓冲、同步和派生状态生命周期成本。

**连线清单（制图必须逐一验收）：** Agent → Runtime 表示任务请求；Runtime → CPU 与 Runtime → GPU/NPU 表示执行放置；CPU ↔ GPU/NPU 表示数据/阶段交接而非 CPU 对 NPU 的硬件直接调度；引擎 → Runtime 表示完成、错误、状态和 QoE 反馈；状态/内存层与各引擎按数据生命周期连接。用“控制”“数据”“反馈”三种图例，不画无定义箭头。

### 右侧决策区（约 42%；三个完整语义模块，序号规范 1、2、3）
**1. 当前优先建设的三类能力**
- **CPU/LLVM 异构快速路径：** 用现有 ISA、微内核、布局与跨处理器阶段分工，降低对单一处理器的依赖；主要涉及 CPU/编译/Runtime。
- **可信 Agent 工具操作：** 权限与目标绑定、真实结果验证和受限恢复；主要由应用/Agent 平台及 OS 承担。
- **异构资源与前台 QoE 协调：** 用阶段关键性、共享内存带宽和设备资源状态调整执行；主要由 Runtime/OS 负责。

**2. 只保留条件性研究的三个问题**
不可由软件日志重建的 Agent 私有进度；跨引擎派生状态的特殊物理有效性；CPU 恢复执行的局部硬件状态。**三者均未被充分公开证据证明需要新增专用硬件。**

**3. 当前不支持的硬件投资**
不以“Agent 专用”之名另立语义 ISA、通用缓存、普通优先级/取消控制或独立唤醒硬件预算；已有软件/已有指令和低功耗平台是必须比较的基线。

### 页脚结论 / 证据
**判断边界：已有工程价值 ≠ 已证明存在新增 Agent 专用硅片价值。**
来源：项目现行 2027–2029 投资组合、公开研究综合报告。此页为研究综合判断，非单篇论文直接实验结论。

## 第 2 页｜Agent 工作负载如何变形

### 标题
**Agent 从单次模型调用变成跨应用、可恢复、需验证实际效果的执行链，增加了 CPU/OS 的控制与状态责任。**

### 顶部定义（投影文字）
**传统推理主要完成“输入—计算—输出”；Agent 还必须处理“执行动作是否被授权、是否真正完成目标，以及状态变化后能否安全继续”。** 这并不意味着每个 Agent 步骤都要由 CPU 执行。

### 主图：一项“调整出行日程”的说明性任务（非实验 trace）
使用五泳道（Agent/App | Runtime/OS | CPU/LLVM | NPU/GPU | 工具/状态），每个节点写明输入、动作、输出。
- **① 请求及约束：** 用户提出调整日程；Agent 拆分目标，Runtime 创建阶段与状态版本。
- **② 检索与推理：** 在用户授权范围内读取日历信息；CPU 组织动态控制，适用的模型算子被放置到 CPU 或 NPU/GPU。
- **③ 授权与目标确认：** 写入前绑定操作对象、权限与当前上下文；这是软件平台信任边界，而非 CPU 指令语义。
- **④ 执行动作与验证：** 工具更新日历，返回状态；Agent 根据外部效果证据核对目标是否实现。失败可能导致重新规划，不应盲目重试有副作用动作。
- **⑤ 暂停、失效与恢复：** 若用户更改目标或过程被打断，旧派生缓存/模型图及工具结果必须按版本/授权重新判断是否适用。

**箭头规则：** 主干 ①→⑤ 用连续实线；验证失败 → ②（重规划）用带标签回环；用户更改请求 → ⑤ → ①/② 使用独立触发箭头；Runtime ↔ 加速引擎标注调度/结果；工具效果验证箭头必须返回 Agent/应用层，而不是直接从工具返回 CPU cache。

### 左右对照与解释区
左侧狭栏“单次推理”结构为：输入→模型执行→输出；旁文“不能覆盖工具副作用与跨应用状态恢复”。右侧列四个**新负担及处理位置**：
- 动态 shape 与不同阶段 → 编译/异构 placement；
- 工具动作的真实效果 → Agent 平台与 OS 权限/验证；
- 可撤销目标和派生缓存 → Runtime 版本化、生命周期管理；
- 前台交互与后台事件 → OS admission、QoE 与低功耗机制。

## 第 3 页｜为何 TOPS 不是异构放置规则

### 标题
**CPU 与 NPU 的阶段选择由端到端总成本决定：内核计算快，不一定能抵消准备、转换、数据搬运和同步。**

### 投影文字：五类成本拆解
一个阶段的实际执行代价近似为：
**T_stage = T_prepare + T_layout/quant + T_compute + T_transfer/sync + T_fallback**。
这里的分项是解释框架，真实实现可能重叠或复用；**不能直接把这条加和当成经过测量的所有手机关键路径模型**。

五项含义：
- **准备**：子图编译、模型/Kernel 可用性、启动与工作提交（可能跨多次调用摊销）。
- **布局与精度**：packed 格式、数据类型变换、量化/反量化；是否可复用决定成本是否重复。
- **计算**：CPU 向量/SME2 kernel 或 NPU graph 的算子执行时间。
- **搬运/同步**：共享内存及跨引擎数据交接、依赖栅栏与等待；共享 buffer 不等于零同步成本。
- **回退**：不能由当前 NPU 软件栈处理的部分在 CPU/GPU 上执行；强 NPU 软件基线可能缩小它。

### 主图：四类阶段的非定量成本构成图
图上方写“**结构示意：只表达成本项目是否相关，不表达真实占比或 CPU/NPU 固定胜负**”。
以四条等宽**勾选矩阵/步骤链**代替伪装真实占比的堆积条：
1. 长 prefill：较大批量计算，可摊销部分准备成本，优化 NPU 可能有优势；
2. 短 decode/小 GEMV：反复小阶段，packing、启动、memory movement 可能敏感；
3. 精度敏感 attention / residual：NPU 低精度与 CPU/GPU 高精度分工会改变边界；
4. 工具/控制阶段：不规则分支、系统调用与权限验证主要体现控制成本，并不等同深度学习算子。

右侧**顺序判定树**：
① 当前 NPU 后端是否高效支持模型算子/精度？→否：考察 CPU/GPU 或改写图；是→
② shape/compiled graph 和 packed data 是否可复用？→否：计入准备与变换；是→
③ 内核收益是否大于搬运与同步及前台争用？→否：保留 CPU/混合路径；是→评估 NPU；
④ 仅在相同模型/设备/版本/测量口径下比较端到端 QoE；此前所有节点是决策逻辑而非真实测得阈值。
