# Round15L — 15 页正文“领导能独立理解”逐页审稿矩阵 v1

2026-10-08。**设计审计而非全套 PPT 改稿已完成**。审查依据：[原始 15 页内容故事板](../content-storyboard-v1-2026-10-08.md)、[V6 领导可读性标准](leadership-readability-gate-v1-2026-10-08.md)、已试制第 5/6/8 页。目标读者：具一般工程素养但不熟悉 Agent LLM、NPU 或微架构的技术管理领导。

## 总体诊断

总体蓝图证据丰富，但仍有三种跨页系统性问题：
- **标题堆积技术名词而非讲结论**，如“LLVM lowering、SME ABI、DAG criticality、QoE”即使术语精确，也无法让非该领域领导立即知道价值。
- **文字给出术语，却没有解释技术动作、它解决的具体障碍，以及该动作关联图中哪一个节点**；尤其 Graph Bucketing、Head-wise Pipeline、状态版本、长链故障恢复。
- **“论文最高××倍”未与实验设备、模型、参照方案和测量层级贴在一起**，读者容易把单个算子能耗看作全任务能耗，或把一组手机实验推广到 2029。

图形侧严禁三件事：未定义箭头端点、不带源的悬空小字、不具实验依据的比例长度。标题和模块说明以自然陈述句表达“障碍→做法→效果”，而非“技术名词集合”。

## 15 页逐页整改方向

以下**新标题是面向管理层的措辞草案**，必须在正式制图前依原始论文和当前投资组合逐条核实限定，不表示这些标题已经写入既有全部 PPT。

| 页 | 建议结论式主标题（尽量一句读懂） | 需要解释/修正的内容 | 图形与证据硬要求 |
|---|---|---|---|
| **1** | **Agent 带来的新负载更需要现有 CPU 灵活执行和系统协同，尚不足以证明需要专用 CPU 指令** | “Agent任务”给一个生活例子；ISA=CPU能执行的指令规范；“有价值的工程投入”≠“新增硬件有证据” | CPU 与 NPU 并列、LLVM 为编译工具；三类工程/平台优先，三类研究储备，0 个专用硅片已证实 Bet |
| **2** | **Agent 要完成跨应用任务，必须把推理、授权、真实操作和结果验证接成完整流程** | “工具成功”不等于“日程确实改好”；为何失败重试有重复执行风险 | 一个日程调整场景，从申请→验证，回环/取消有不同原因和终态 |
| **3** | **选择 CPU 还是 NPU，要比较整个阶段的完成时间，不能只看算子速度** | 图准备、格式转换、数据同步、回退各是一种什么成本；何时被重复支付/复用 | 公式仅作成本解释、无真实数据不画伪占比；展示至少一例“内核快但总时间不快” |
| **4** | **一组 Snapdragon 实测显示：NPU 某些计算更快，但完整阶段未必同幅度提速** | Prefill/Decode 是什么意思，6 CPU 核是怎样的 baseline，kernel vs aggregated operator 各测量什么 | 三实验口径分开；Table III `call-usec` 包含调用/通信，不能标为纯 NPU 计算时间 |
| **5** | **ShadowNPU 让 NPU 找出重要 Token，CPU/GPU 只精算关键部分** | 旧 llm.npu 的 Attention 分工为何；Graph Bucketing 支撑哪个节点；Head-wise 流水针对哪些步骤 | 两论文清楚分栏；三段显性箭头；4.5× e2e MI14 vs C/G-Full；7.7× 为 K60 单 kernel 能耗；0.4pp 准确率单独注明 |
| **6** | **vivo X300 上 SME2 加快了 CPU 模型计算，但数据布局转换仍占用大量时间** | SME2 是既有 CPU 矩阵扩展，不是独立 NPU；解释“Data Movement”指本文模型的布局和搬运 | 单核 CPU、Normal mode、SqueezeSAM，OFF/ON、ms真实轴；不能外推 Agent 端到端收益 |
| **7** | **SMEPilot 让 CPU 内不同执行方式更好分工，减少等待和重复整理数据的时间** | SME 属于 CPU；tile=把大矩阵分块；packing=重排数据以更好访问；为什么规划/流水可减少空闲 | 方法图每个术语旁要有输入/动作/产出；ablation 每组必须交代移除什么、设备和延时口径 |
| **8** | **HeRo 优先推进关键任务，避免处理器争抢共享资源，使手机 Agent 更快完成工作** | DAG=有先后依赖的任务图；ready任务=前置工作已完成；哪步决定先做谁、哪步选CPU/NPU | 采用已获“清楚多了”反馈的 V6 逻辑；Eq4/Eq1 必带直观语言；C1/C2 baseline 为 Ayo-like |
| **9** | **CPU 编译优化能提高局部计算效率，Agent 全任务收益还取决于 Runtime 和 OS 的协同** | LLVM 把模型计算转换为 CPU 可用代码；SME ABI 是使用这些指令时的调用/状态约定；“谁能负责什么” | 区分 Compiler、CPU、Runtime、OS、Agent 工具所有权；不把编译器画作运行时处理器 |
| **10** | **安全执行工具操作要核验权限和真实结果；复用计算状态还必须确认它没有过期** | 工具动作和派生计算结果是**两种不同问题**，举“取消日程”和“缓存来自旧任务版本”例子 | 两条并列轨道分别给原因→检查→结果；若有关联，明确是版本/来源约束，而非想象出的新硬件协议 |
| **11** | **主动 Agent 应先判断是否值得帮助用户，再决定是否唤醒高功耗计算** | 低功耗传感与完整 LLM 并非同一耗电量；不打扰、隐私同帮助率一样重要 | “不行动”也必须是正常终态；标出现有 CHRE/感知基线，不宣称已需新 LP 核 |
| **12** | **软件办法用尽后仍有明确硬件独有价值，才值得考虑 Agent 专用 CPU 设计** | “软件可替代性”“物理因果”用普通话解释：已有软件改进还能不能解决、为什么必须用新硅片 | 四个证据门每门用一个简单问题加后果；无证据=保留研究，不冒充永远不可行 |
| **13** | **优先建设三类现有技术能力；三项硬件问题先研究，不批准新的 Agent 专用硅片项目** | Build、Reserve、Watch、Kill 尽量换成“优先建设／条件研究／持续关注／当前不支持” | 投资类型、解决的问题、证据、所有权完整呈现，内部研发代号不在正文出现 |
| **14** | **先完善已有 CPU 能力，再打通系统协同；新硬件需等到有充分证据** | 2027/2028/2029 是**建议先后顺序**而非芯片量产计划；解释接口和上下游依赖 | 年×技术层矩阵，每格写“今年解决哪个具体问题+相较去年新增什么”；不许虚构预算/OEM发布时间 |
| **15** | **现在应明确优先做什么、由谁负责，以及哪些专用硬件暂不投入** | 决策请求应是管理层可答复的问题；所有权为技术建议不是已经授权的组织安排 | 三个可回应的议题：优先级、跨团队责任、重新打开硬件判断的证据条件 |

## 重大问题与优先级

### P0：在继续制作对应 PPT 前必须先完成内容级修改

- **第 4、5、6、7、8 页涉及论文数值**：每个结果都显示**指标 + 对照方案 + 设备 + 测量层级**。特别检查“内核／阶段／端到端／整机”的误替换。
- **第 5、7、8、9、10 页涉及机制图**：每项技术点必须明确支撑哪一步，某个节点输出什么、交给谁；非专业读者能在一张图中看出“这样做的理由”。
- **第 1、12、13、14、15 页涉及投资判断**：统一三类工程/平台优先、三项条件研究储备、0个当前独立 Agent 专用 CPU 硬件 Bet，不因漂亮图形改变判断。

### P1：改写用词与演讲层次

- 在第 1 页首次定义 Agent；第 3 页说明 Prefill/Decode；第 6 页定义 SME2；第 7 页定义 tile/packing；第 8 页定义 DAG/ready task；第 9 页定义 ABI、LLVM；第 10 页定义派生状态；第 11 页定义 CHRE；第 13 页去掉内部代码。
- **不强行把英文专业名称翻成不明所以的中文**：`batch size`、`Graph Bucketing`、`Head-wise Pipeline` 可保留英文，但必须附“调整哪个参数／支撑哪个主流程节点／影响什么成本”。
- 若某页无法容纳公式和说明，正文优先保留有独立意义的两个公式与自然语言解释，其余进技术附录。公式不可只作为学术装饰。
- 表格或小卡片不能仅列“技术是什么”，必须写“遇到什么障碍→采取什么动作→产生什么改善/决策”。

## 固定的“四问”页面验收

1. **这一页想让我得出什么结论？**（只有看标题即可回答）
2. **我为什么应该相信这个结论？**（能看到论文、清楚的 baseline 和限定）
3. **图上的每个重要步骤/小字有什么用？**（有明确输入、动作、输出和支撑节点）
4. **它对 CPU/LLVM 或跨团队决策有什么影响？**（有行动/保留/否决的明确边界）
