## 2. 已在 PPT 中实际展示的核心结论

**标题**：**只有现有软件难以解决、且手机端收益得到验证时，才有依据考虑 Agent 专用 CPU 硬件。**

**解释句**：发现 Agent 性能问题，不等于证明必须新增 CPU 指令或电路；应依次检查四类证据。

**模块结论**：四道证据检查：任何一项缺乏可信依据，都不能直接推出新硬件立项。

### 四道问题（研究团队设计的审查框架，非现成行业规范）

1. **手机 Agent 负载中，确实反复出现这个瓶颈吗？**  
   需要有可复现的手机任务、发生频率与阶段时延/能耗/用户体验影响，不能只引用服务器或概念系统。
2. **充分优化的软件与现有 CPU 指令仍不够吗？**  
   至少检查 LLVM / SME2、CPU 微内核、优化后的 NPU 后端、Runtime 与 OS 通用能力；与弱软件基线比较不能证明专用硬件必要性。
3. **是否找到软件不能低成本替代的物理原因？**  
   明确候选新增的电路、可见状态或控制点，证明日志/检查点、版本化状态、已有缓存或通用控制仍存在可重复、可定位的剩余损失。这里不是要求数学意义上证明任何软件在任何时间都绝对无法实现。
4. **额外硬件在手机上带来的收益值得吗？**  
   在相同设备、模型和软件口径下测量整机响应、用户 QoE 与能耗，同时估计面积、验证复杂度、静动态功耗与兼容风险。没有同条件数据不得宣布新设计已经有效。

**结果图**：只要有一项证据不足，应优先推进现有工程改进或开展有界条件研究；只有四项均得到充分可靠证据，才进入新硬件原型/代价验证。这是**建议的立项审查门槛，不是企业已批准的正式审批流程**。

## 3. 三个仍需回答的研究问题（不可在领导页显示内部研究代码）

- **Agent 任务进度**：中断后影响结果的关键信息，是否存在软件日志/检查点与完整可观察历史仍无法重建的部分？需首先核实信息独有性与恢复代价。
- **跨处理器派生数据**：用户任务/模型/权限改变后，CPU/NPU 的缓存、packed tensor 或计算图是否可用版本、来源核验及通用同步机制管理？真实剩余同步/失效开销是多少？
- **CPU 恢复执行的局部性**：任务暂停、迁移与恢复后，缓存/TLB 等状态的重预热损失，在现有 CPU/OS 调度亲和性和通用共享缓存机制对照下是否仍显著？

三者都不是**已经验证需要新电路的独立硬件建议**。不将用户目标语义直接赋予 PSTATE/SME 等现有 CPU 架构状态，也不把 SME 和 CPU 核画成不同 SoC 处理器。

## 4. 依据的范围与不能推出的结论

本页是**公开技术资料和研究成果的综合判断**，不是论文 Figure 的复刻、单篇论文所定义的“四关规范”或作者已经做出的新硬件实验。

| 来源 | 已有技术证据 | 不能据此推断 |
|---|---|---|
| [When NPUs Are Not Always Faster](https://arxiv.org/abs/2605.27435) | 受测移动 CPU/NPU 推理阶段性能受部署后端、fallback 和调用开销影响 | Agent 专用 CPU 指令必有独立收益 |
| [HeRo](https://arxiv.org/abs/2603.01661) | Agentic RAG 的阶段映射/争用控制可由软件 Runtime 优化 | 异构调度问题必需交给新硅片解决 |
| [LLVM AArch64 SME](https://llvm.org/docs/AArch64SME.html) | 已有 CPU SME ABI/streaming、SM/ZA 编译处理规则 | PSTATE.SM 操作的量产手机时延已经在本页实测；SME 是独立 NPU |
| [Android CHRE](https://source.android.com/docs/core/interaction/contexthub) | 低功耗处理器的 nanoapp 环境与 AP offload 是真实存在的系统基础 | 新 Agent-only 低功耗硬件必需或永远没有价值 |
| [本项目现行技术路线](https://github.com/xjs-work-lab/agentic-CPU-uArch/blob/main/09-roadmap/current.md) | 当前公开证据支持三类工程/平台工作、三项条件研究、没有可以确证的新增 Agent-only CPU-uArch 方案 | 不应把历史内部打分、旧 Primary Bet 或尚未验证的创新放入管理决策页 |

专利只能证明某种技术主张已经公开/申请，不能替代可比手机测量、产品性能或实施自由判断（FTO）。
