## 1. 投影展示内容及任务

**主标题**：**主动 Agent 应先筛掉无关事件，再按需唤醒 CPU/NPU；优化目标是减少无效耗电与误打扰。**

副标题：持续感知不等于持续运行大模型：先做轻量判断，只有有价值的候选任务才继续执行。

正文核心：**已有低功耗处理能力可用于“前置过滤”；完整 Agent 仍需按任务分级决策。**

原创说明场景：由运动传感器/活动变化形成“是否需要提醒用户出行”的候选，低功耗侧先对平台支持的传感器信号初筛；**进入应用 CPU 后**结合日程、用户权限和当前情境判断事件是否有帮助。必要时才按平台支持条件调用 GPU/NPU 做复杂模型计算，最后由 Agent/App 层考虑实际通知或操作。示意并非量产设备的真实执行 trace。

**分支规则**：
1. 低功耗平台筛掉无关/不满足条件的事件 → 不需要唤醒应用 CPU。
2. 进入 CPU/Runtime 后发现帮助价值有限或打扰风险高 → 不行动或延后处理。
3. 用户确有需要 → 选择适合计算的处理器执行；必要时 NPU/GPU 参与推理；由 Agent 在权限允许范围内决定后续受控动作。**不是每条事件都必须走三段，也不宣称 NPU 始终被唤醒。**

**重要硬件层级**：CHRE 为低功耗处理器上的软件执行环境，Qualcomm Sensing Hub 为厂商低功耗处理体系，AP CPU 是不同的处理域；CHRE 不是普通 CPU 的一个指令集扩展。上图是软件分级决策示意，不能被描述为 Android/Qualcomm 已共同提供单一“Agent 专用语义唤醒 API”。

## 2. 三类证据分层

### 已证实的官方基础能力

- [Android CHRE](https://source.android.com/docs/core/interaction/contexthub)：提供低功耗处理器上运行 nanoapp 的 API，用于部分传感器、位置、Wi-Fi、音频等相关任务，避免一些频繁的主应用处理器 AP 唤醒。不同手机平台上的功能支持不尽相同；CHRE 不意味着第三方 App 可以任意直接访问。
- [Qualcomm 第2代 Sensing Hub 官方技术介绍](https://www.qualcomm.com/news/onq/2021/07/brand-new-ai-runs-2nd-gen-qualcomm-sensing-hub)：介绍低功耗、上下文感知及小模型离载至专门处理器的能力。资料中的厂商表现描述不等于完整 Agent 工作负载的真实手机续航数据。
- [Android Doze 和 App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)：Android 对后台 CPU/网络工作采用延后及限制机制；主动 Agent 应尊重电源管理、后台运行、系统授权边界，而非随意绕过唤醒限制。

### 本研究提出的工程推断（尚非单篇论文实验结论）

把事件感知/过滤、AP 上下文价值判断、可选模型计算以及用户实际操作分成不同阶段，并保留“不行动”这一合法输出。首先在现有低功耗与通用 CPU/OS 机制上推进触发条件、负载分工和电源管理。推断来自多来源系统综合，不代表 CHRE 内已经实现了复杂 Agent 价值评估算法。

### 尚缺独立公开证据

没有同一手机、同一事件触发集和相同权限/用户帮助标准下，完整主动 Agent 的**有用率 / 打扰率 / 漏提醒 / 全天整机能耗 / 端到端 QoE**共同比较，不能据此给出虚构的百分比收益。尚无足够证据把低功耗主动 Agent 的需求直接解释为需要**新的 Agent-only 专用 CPU 唤醒硬件**。

## 3. 验证建议（未执行实验）

以同一设备和事件集对比：
- 基线 A：满足权限/后台规则条件下由 AP/模型直接处理更多候选事件；
- 方案 B：低功耗前置筛选 + AP 上下文判断 + 适用场景中按需调用 NPU；
- 记录：误触发与漏提醒、唤醒次数和唤醒链路、待机/整机能耗、推理阶段耗时、用户实际帮助与打扰指标，额外记录隐私权限和 OS Doze 影响；
- 控制：相同目标事件、传感器可用性、软件版本、模型精度、背景应用负载和通知策略。
- 数据不足时仅提出 PoC，不虚构新硬件收益或立项结论。
