## 1. 领导需要带走的一句话

**Agent 的任务存在前后依赖；CPU、GPU、NPU 也会争抢共享资源。HeRo 优先推进影响整体完成时间的任务，并为它选择合适的执行方案，避免局部算得快、整项任务反而慢。**

这是技术综合解释，不是手机 Agent 的所有负载都同样遵循的硬件规律。**整页唯一中心论点**：HeRo 演示了手机端动态 Agent 工作流的软件调度空间，不是独立 Agent 指令集的实验证明。

### 锁定标题（陈述句，能独立表达观点）

- **整页主标题**：**HeRo 通过优先处理关键任务、合理分配 CPU/GPU/NPU、减少资源争抢，加快手机 Agent 任务完成**
- **机制模块标题**：**HeRo 先确定哪些任务最影响整体进度，再选择合适的处理器和执行方式**
- **数据模块标题**：**论文两组手机实验均显示：针对特定 Agentic RAG 工作流，动态调度比静态分配耗时更短**
- **底部技术启示**：**对 CPU 团队的启示：优先与 Runtime/OS 协作优化跨处理器调度；这不直接证明需要新增 Agent 专用 CPU 指令。**

禁用标题：`联合评估 xPU 性能、batch size 与 DRAM 争用`、`调度器的五个阶段是什么？` 等堆名词或只有问题的标题。

## 2. 五步骤：讲清楚为什么需要、输出给下一步什么

| 节点 ID | 卡片标题（领导第一眼） | 卡片内部解释（中文，允许必要英文） | 交给下一步的输出 |
|---|---|---|---|
| H1 | **1 找出当前能做的任务** | Agent 有些步骤需要等待前序结果；调度器只从**依赖已满足**的任务中挑选。 | `ready list`（当前可执行的任务列表）→ H2 |
| H2 | **2 优先处理关键任务** | 不仅估计眼前已知道的下游任务，还考虑未来可能出现的任务，优先避免拖慢整条任务链的步骤。 | **被选中的关键 ready task** → H3 |
| H3 | **3 比较不同执行方案** | 同一任务可能交给 CPU、GPU 或 NPU；批量任务还要比较不同 `batch size`，流式处理可以用 `token group` 划分。 | **可行的处理器/分批配置及预计耗时** → H4 |
| H4 | **4 避免资源互相争抢** | CPU/GPU/NPU 同时运行可能争用共享内存带宽。筛除带宽超限方案，并估计对正在执行的关键任务的拖慢程度。 | **带宽允许、且经过代价评分的配置** → H5 |
| H5 | **5 选择并执行合适方案** | 选择兼顾任务完成时间与资源影响的配置，派发当前子任务。完成后更新任务依赖与资源状态，再开启下一轮。 | **当前任务已派发；完成后更新 ready list** → 下一轮 H1 |

### 箭头合同（页面不显示 ID）

- H1 → H2：`可执行任务列表`
- H2 → H3：`当前优先推进的任务`
- H3 → H4：`候选执行配置与预计耗时`
- H4 → H5：`带宽可行的候选及综合评分`
- H5 回到 H1：**仅用底部短句**“完成一个任务后，更新依赖，继续下一轮”，不画一根绕过整张图的长返回线。

**纠错**：一个子阶段被映射到一个合适处理器，**不意味着全流程只有一个处理器执行**；不同子阶段可能在 CPU/GPU/NPU 上并行。这是带宽约束有用的原因。没有可行执行配置时应等待或换一个 ready task，而不是盲目派发。

## 3. 专业术语应当出现在哪里

主阅读路径中优先使用**可执行任务、关键任务、候选处理器、共享内存带宽**这些能被理解的概念。

| 若需要出现的术语 | 必须附带的解释 |
|---|---|
| `DAG` | 带有先后依赖的任务关系图；不懂 DAG 也不影响理解 H1 |
| `xPU` | CPU/GPU/NPU 等异构处理器的统称；**不得当成第四个处理器** |
| `batch size` | 一次交给模型执行的工作量；大批次不一定总耗时更短 |
| `token group` | 流式生成中按若干 token 划分的执行单元；**不是 Eq.3 的 batch-size 优化变量** |
| `DRAM contention` | 多个处理器争抢共享内存带宽，可能互相拖慢 |
| `criticality` | 该任务若延后，可能多大程度拖慢整个工作流的完成 |

正文无需解释 `G_obs(t)`、`R(t)`、`A(t)`、`v_cand`、`v*`、`B_soft` 的全部数学符号；它们属于学术备注/附录中的专家层。

## 4. 公式服务于直观解释，而不是取代解释

第 8 页可保留**最多 2 条视觉主公式**，其余公式放入备注/专家附录。建议保留：

**① 为什么不能只选最先就绪的任务（论文 Eq.4）**

\[
CS(v)=CS_L(v)+\beta CS_F(v)
\]

> 中文解释：任务优先级同时看**已经能观察到的后续影响**和**未来可能出现的后续影响**。不是单纯先来先服务。

**② 为什么有空闲处理器也不一定应该立即并行（论文 Eq.1 的概念化形式；真正原式以论文和 V3 数学合同为准）**

\[
p_v(c,B(t))\approx p_v^0(c)\,\phi_{v,c}(B(t))
\]

> 中文解释：某任务预计运行时间不仅取决于单独跑有多快，还取决于共享内存带宽争用可能造成的减速。

对 H3 的 `batch size`：正文以“**工作分成几批 × 每批耗时**”的口语逻辑说明，论文 Eq.3 完整公式可在 PPT 备注和附录保留。这样无需在一页同时解释三个复杂公式的所有参数；如用户强调第 8 页三公式并列，必须拆分为第二技术补充图，不能以缩小字号实现。

**每个公式区块必须有“结论句 → 公式 → 一句现实含义”**，且通过连线或角标关联 H2/H4，而不是放在视觉上无关联的公式池。

## 5. 实验结果如何让非专业领导读懂

- 研究范围：商业手机平台上受测的 Agentic RAG 工作流；不代表任何手机或 Agent 应用均得到相同倍数。
- 场景 1：对照方案 **5.79 s** → HeRo **3.82 s**；明确是同一受测配置的比较。
- 场景 2：对照方案 **17.23 s** → HeRo **5.38 s**；另一个模型/工作流组合，不和第一组作跨场景条长比较。
- 如果页内有容量，标注 `Ayo-like static mapping` 是论文基准的具体名称；第一视觉层可解释成**固定分配处理器的方案**，准确 baseline 名称写在小字来源。
- 页面主结论不是“10.94×”或“CPU 一定更快”，而是**根据任务依赖和资源压力动态调度，能够在这些实测条件下降低任务耗时**。

- 如果空间冲突，应当先精简英文符号与装饰、减少重复文字、把完整公式转到专家附录，而**不是把所有中文缩到不可投影**。

## 7. 非专业领导验收 Gate

在不给口头讲解、遮住论文原文、只读一张 16:9 幻灯片的情况下：
1. **10 秒内**能说出“哪类问题？HeRo 用什么整体思路解决？”；
2. **30 秒内**能顺着每一步说明它为什么需要、怎样影响下一步；
3. 能看懂两个公式对应 H2/H4 的现实意义，即使不理解变量下标；
4. 能判断两组数据比较的是“什么方案 vs 什么方案”，而不是误会为所有 Agent 手机都有固定提速；
5. 能区分**论文证明的软件调度价值**与**未证明的 Agent 专用 CPU 硬件价值**；
6. 若至少一项做不到，先回改**文案/叙事/版面**，不得先通过美化背景或再塞术语来解决。
