## 页 1：总览——为何投软件/现有 ISA，而不急于新增 Agent CPU 指令？

**锁定标题**：手机 Agent 提升 CPU 的可编程控制、选择性 AI 执行与异构协同价值；目前不支持为 Agent 单独新增 CPU 指令集。

**锁定导语**：面向 2027–2029 年，建议优先建设现有 AArch64/SME2 的 CPU/LLVM 快速路径、可信工具执行和跨引擎 QoE 管理。当前公开证据不足以支持独立的 Agent 专用 CPU 硬件立项。

### 左模块标题（锁定）
**一个 Agent 目标如何经过 Runtime/OS 分工，最终落到 CPU、GPU 与 NPU？**

固定节点及解释（纵向“请求→调度→并行执行→反馈/状态”，不是 CPU→GPU/NPU 的单列关系）：
- **Agent / App：定义目标并调用工具**。拆分目标、发起推理/检索和跨 App 操作，必要时重新规划。
- **Runtime / OS：协调执行与资源**。综合任务依赖、前台 QoE、权限和设备资源，将阶段放置到合适的执行引擎。
- **CPU / LLVM：承担可编程控制与选择性计算**。处理动态分支、不规则短阶段，并使用现有 Neon/SVE/SME2 和微内核加速适合的算子。
- **GPU / NPU：执行适合的模型算子**。承担适配良好、可有效摊销启动和数据交接成本的计算阶段。
- **内存与派生状态：支持跨引擎共享和恢复**。数据布局、版本、同步、生命周期影响端到端成本。

箭头强制关系：Agent → Runtime（请求）；Runtime → CPU 与 Runtime → GPU/NPU（执行放置）；CPU ↔ GPU/NPU（阶段数据交接）；引擎 → Runtime（执行结果/资源反馈）；内存/状态 ↔ 两类引擎（读写与有效性）。不得画成 CPU 统管 NPU 的硬件控制信号。

### 右模块标题（锁定）
**基于目前公开证据，哪些能力值得优先建设，哪些只应保留观察？**

- **1 优先建设（3 类工程/平台能力）**：CPU/LLVM 现有 ISA 快速路径；可信 Agent 工具操作与效果验证；Runtime/OS 异构调度与前台 QoE。
- **2 条件研究储备（3 个未证实问题）**：Agent 私有进度信息；跨引擎派生状态的物理有效性；CPU 续执行局部性。三者均需额外独立公开证据，不能直接当作新硅片项目。
- **3 暂不支持立项（专用硬件）**：独立的 Agent 语义 ISA，以及缺乏软件不可替代性证据的专用缓存/Hint/通用优先级功能。

**底部结论（锁定）**：工程优化有价值，并不等于已经证明需要新增 Agent 专用硅片。

## 页 2：Agent 为什么使系统控制和状态管理更重要？

**锁定标题**：Agent 从单次推理扩展为跨应用、可恢复且需核验实际效果的执行链，CPU/OS 因此承担更多控制与状态责任。

**锁定导语**：以下以“调整出行日程”为说明性场景，不代表任何论文实测轨迹；CPU 负责部分控制与计算，适合的模型阶段仍可由 GPU/NPU 加速。

### 主模块标题（锁定）
**为完成一次真实日程调整，系统必须如何从计划走向授权、执行和验证？**

**沿横向从左至右的六阶段**（每阶段仅放一条主要文字；无要求在所有列填满五泳道小卡片）：
1. **理解请求**：识别用户目标与约束。
2. **规划任务**：拆解检索、推理与工具步骤。
3. **选择执行路径**：Runtime 根据阶段需求安排 CPU/GPU/NPU。
4. **确认授权与目标**：写操作前绑定权限、对象和最新上下文。
5. **执行工具动作**：调用外部应用并收集效果记录。
6. **验证和恢复**：核验实际状态；失败或变更时重新规划，避免盲目重复副作用。

**结构节点/泳道**：Agent/App 负责目标、推理计划和效果核验；Runtime/OS 负责阶段调度、权限约束和状态恢复；CPU/LLVM 负责不规则控制与适用短阶段；GPU/NPU 负责适用模型算子；外部应用负责真实读写及回执。只在参与步骤的泳道画节点；不要把所有阶段×所有泳道塞满文字格。

**回环精确定义**：验证失败 → 回到规划（标“目标未完成，重新规划”）；目标变更/中断 → 状态版本与授权再检查（标“旧结果可能失效”）；工具返回 ≠ 实际目标已完成。

### 右模块标题（锁定）
**与单次模型调用相比，哪些系统能力直接关系任务能否安全完成？**

1. **动态阶段分工**：减少不适宜引擎的准备、同步和回退开销。
2. **工具权限和目标绑定**：避免误操作或越权执行。
3. **真实效果验证**：区分工具返回成功和用户目标实现。
4. **版本化状态与安全恢复**：避免目标变化后复用失效缓存或重复副作用。

**底部结论（锁定）**：Agent 的关键增量是“正确完成跨应用任务”，而不只是让单次推理更快。

## 页 3：异构执行为何必须关注总时延？

**锁定标题**：CPU/NPU 的执行位置应按端到端总成本选择；内核算得更快，不一定能抵消准备、转换和同步的额外开销。

**锁定导语**：阶段选择需同时考虑模型后端支持、数据布局复用、计算执行、跨引擎交接与回退，不能仅凭 NPU TOPS 或单一 Kernel 速度下结论。

### 左模块标题（锁定）
**一个阶段的实际完成时间，为什么不只等于算子计算时间？**

**锁定公式（仅作解释性分解）**：
`T_stage ≈ T_prepare + T_layout/quant + T_compute + T_transfer/sync + T_fallback`

沿左至右排五项，名称及下方一句解释固定：
- **准备**：模型/子图准备与工作提交；可能复用摊销。
- **布局/精度**：packing、量化及格式调整；可复用性重要。
- **计算**：CPU 或 NPU 的算子与图执行。
- **交接/同步**：共享缓冲、数据交接与等待。
- **回退**：当前 NPU 软件栈无法高效执行的部分。

**限制注解（锁定）**：公式是概念性成本分解；实际阶段可能并行重叠，不能当成通用手机实测时延方程。

### 中模块标题（锁定）
**不同工作阶段，为什么会使 CPU 与 NPU 的最优分工不同？**

使用横向三列单一阅读路径“工作负载特征 → 可能显著的系统成本 → 执行放置含义”。**不画纵横都能读的卡片矩阵**。四行：
- **长 Prefill / 密集计算** → 大算子计算与准备摊销 → 优先评估优化后的 NPU，但仍考虑传输成本。
- **短 Decode / 小 GEMV** → 反复启动、内存访问和布局 → CPU/SME2 或 NPU 谁快取决于具体形状、版本和端到端测量。
- **精度敏感的 Attention 子阶段** → 数据精度与回退路径 → 可能需要 NPU+CPU/GPU 分工，优化 NPU 软件会改变边界。
- **工具/系统控制阶段** → 分支、权限、I/O 和状态等待 → 主要是 CPU/OS 控制路径问题，而非 NPU 大吞吐优势问题。

**数据性质**：以上全是机制推理和负载分类，**不是已经测得各行处理器获胜的实验结果**；不使用假比例、假百分比和伪装成数据的颜色宽度。

### 右模块标题（锁定）
**为了降低端到端时延，应该按什么顺序决定执行引擎？**

1. **后端支持**：优化后的 NPU 是否支持所需形状、精度和算子？
2. **可复用性**：已编译子图与 packed 数据能否被多次使用？
3. **协同成本**：Kernel 收益能否覆盖搬运、同步、回退和前台 QoE 代价？
4. **最终判断**：在相同设备、模型、精度与软件版本下比较完整阶段时延，选择 CPU、NPU 或混合执行。

**底部结论（锁定）**：优化目标是减少实际任务的整体时延，而不是追求单一处理器最高理论算力。
