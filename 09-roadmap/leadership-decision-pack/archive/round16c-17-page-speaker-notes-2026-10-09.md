## 03 / 17

一、页面内容详细讲解

这是正文第一张总体判断页。左侧图从上至下依次是四种不同概念：① Agent/应用接收目标、规划任务、发起工具操作并核验结果；② Runtime/OS 软件层根据任务先后依赖、用户当前交互优先级和资源压力进行分工；③ CPU 与 GPU/NPU 是可以选择的不同计算资源，分别适合不同阶段；④ 共享数据/状态层涉及布局转换、同步、缓存版本与数据有效性。箭头表示软件请求或结果反馈，不是一根由 CPU 直接控制 NPU 的硬件线路；LLVM 是产生 CPU 代码的编译工具，不是独立处理器。

右侧把研究结论分成三个层次。第一层是“优先建设”的三个工程/平台方向：其一优化既有 CPU ISA 上的编译生成、微内核和数据布局；其二使 Agent 工具调用知道操作谁、依据什么权限，并核验外部真实效果；其三由 Runtime/OS 结合阶段特性、QoE 和带宽争用安排 CPU/GPU/NPU。三类方向的技术责任域并不相同，不能说都由 CPU 微架构团队单独交付。

第二层是三个条件研究问题：任务的关键进度信息是否真有完整软件日志仍不可重建的部分；跨处理器派生数据有效性是否需要版本/来源检查之外的新增物理机制；CPU 被中断并恢复后，是否仍有普通亲和性/缓存机制无法缓解的局部性损失。问号意味着目前没有充分证据确认新硬件收益，不等于三套已成熟的硬件设计。

第三层是“当前不支持”：从现有公开材料尚不能认定新增 Agent 专用 CPU ISA 或新硅片是独立成立的优先方案。要强调“值得开展现有 CPU 和系统工程优化”与“新增特殊硬件必要性已经证明”是两个不同判断。本页是跨来源综合技术示意，没有实测性能比例或量产 SoC 连线图；后续几页分别提供事实依据。

## 04 / 17

一、页面内容详细讲解

这页回答“为什么 Agent 对 CPU/OS 提出了不同于单次模型推理的需求”。画面上方是一条六阶段的概念任务链，使用“出行前把某场会议时间改好”为日常例子；这是为了说明因果，不是真实手机的执行追踪。第1步理解请求：找到用户要更改的会议及时间、账户等约束。第2步规划：决定哪些信息要查询、何时需要模型。第3步读取与推理：读取得到授权的日历，适合 CPU 的短控制工作和适合 NPU 的模型算子可按实际软件栈选择，二者并非每次都同时运行。第4步确认写入：检查目标对象、权限及动作风险。第5步调用工具：由日历应用真正提交修改，得到工具回执。第6步核验效果：重新读取日历，与用户的最终目标比对，才决定完成、重试还是停止。

箭头反映顺序关系，而不是每个 Agent 必经且等时的固定硬件流水线。特别注意第5→6步：API 返回成功不能证明业务目标成功，写入也可能选错日历、账号或因延迟未生效。下方的传统模型调用三步“输入→模型计算→输出回答”说明传统任务常在输出文本后结束，不保证外部系统状态；右下两条异常处理则进一步说明为什么 Agent 需要控制与状态管理。

如果核验发现没有改成功，应先核实当前真实状态和幂等性，再决定是否重新规划；带副作用的写入不能无脑重发。如果用户取消、权限失效或任务目标发生改变，应停止旧动作、重新判定授权和状态，必要时安全终止，“取消”不必被解释为必须再尝试一次。底部职责归属强调 Agent/App 管目标、权限与结果，Runtime/OS 管分派与运行状态，CPU 适合控制和部分算子，GPU/NPU 承担适配的模型计算，真正修改仍由外部工具或应用完成。下一页开始分析把模型阶段交给不同处理器时应计算哪些系统成本。

## 05 / 17

一、页面内容详细讲解

上一页说明 Agent 任务含多个模型与非模型阶段，这页进一步回答 CPU 或 NPU 的选择标准。上方五个相连的成本模块是一个定性核查清单，而不是从某台手机测得的五块耗时比例图：①准备模型、子图或提交任务；②精度和数据布局转换、打包；③CPU Kernel 或 NPU 算子实际计算；④跨处理域复制、同步、等待；⑤当前 NPU 软件后端不支持某个算子时，CPU 承接执行。并非所有任务都有五项成本，也不保证它们严格串行或能从不同实验中相加；图准备和数据重排有时可以缓存复用，流水并行也可能与其他开销重叠。

左下表按任务阶段解释为什么不同阶段对成本的敏感程度不同。长 Prefill 是处理较长输入、计算密度相对高的模型阶段，准备成本可能被大量计算分摊，但仍需看支持的精度和图。短 Decode 是一次次生成 Token 的阶段，计算粒度较小，频繁提交、同步和数据交接的相对代价可能更显著。混合精度 Attention 一方面需要足够精度，另一方面可以让 NPU做筛选、CPU/GPU计算难以低精度处理的部分，是否划算依赖后端覆盖。工具/控制类任务含权限判断、分支与系统调用，并非矩阵运算，把它们直接按 NPU 峰值 TOPS 衡量是错误的。

右侧的决策顺序从后端可行性开始：先查当前 NPU 后端是否支持具体算子、精度及输入形状；不支持时考虑 CPU fallback、图优化或其他路径。支持也不保证整体快，需要把准备、格式、调用、同步和回退都考虑进去；最后在相同设备、模型、精度、软件版本和前台 QoE 条件下比较真实阶段时间与能耗。该流程不是一个从理论 TOPS 直接推算手机总体性能的公式。

结论是“没有固定的 CPU 胜或 NPU 胜”，并不是否认 NPU 的吞吐优势，而是强调现实软件栈决定了实际阶段代价。下一页用 Snapdragon 的三个不同测量口径给出实例。

二、来源逐条解读

来源 1｜[研究论文] When NPUs Are Not Always Faster: A Stage-Level Analysis of Mobile LLM Inference，Pu Li、Jiawen Qi、Qinyu Chen 等，2026，https://arxiv.org/abs/2605.27435
主要观点与论据：在受测移动 CPU/NPU、模型与推理后端上，Prefill 与 Decode 的执行性能、NPU调用开销和 CPU fallback 会改变实际阶段表现；论文使用不同表格分别记录算子调用及相关汇总指标。
支撑本页：需要在实际设备与软件后端下比较完整阶段成本，而不以单个计算单元峰值判断。
不能证明：五项成本是来自同一分解表的互斥百分比、CPU 永远更快、或所有手机适用相同阶段边界。

来源 2｜[研究论文] Fast On-device LLM Inference with NPUs (llm.npu)，ASPLOS 2025，https://xumengwei.github.io/files/ASPLOS25-NPU.pdf
主要观点与论据：优化 NPU 静态计算图复用和 CPU/NPU 的模型算子分工，证明后端软件实现会显著影响哪些模型部分适合 NPU。
支撑本页：NPU 软件优化必须纳入强基线；“后端支持”是具体软件能力而非硬件峰值。
不能证明：本页的五项成本来自该文单独完整定量拆分，或所有精度/输入都由同一 NPU 路径高效执行。

本研究综合推断：先核对后端、再在相同条件下比较真实阶段 QoE/能耗，避免一开始预先指定唯一处理器。

## 06 / 17

一、页面内容详细讲解

本页将上一页的定性成本分析转换成一组论文实测。测试场景为 Snapdragon 8 Gen 3（含受测 Hexagon NPU）上的 Qwen3-4B，CPU对照使用6线程，软件和量化格式以原论文报告为准。图上三栏都是“时间越短越好”，但前两栏单位是微秒 μs、第三栏单位是毫秒 ms，横向柱子的刻度也不相同，不能用三个栏的柱子长度直接互比。

左栏①为 Prefill 阶段的一次 MUL_MAT 调用，即处理提示输入时的矩阵乘法。在作者的受测调用路径中 CPU 为 7181 μs，NPU call-usec 为 10352 μs，当前这一次计算/调用是 CPU 快约1.44倍。强调 NPU 的 call-usec 包含调用、通信等路径开销，绝不是 NPU 纯内核计算时间。中栏②换成 Decode 阶段的一次同名运算：CPU 为 324 μs，NPU call-usec 为 210 μs，此时 NPU 快约1.55倍。这两栏已说明阶段、粒度、软件开销会改变赢家。

右侧的 2026 年 ShadowNPU 将问题进一步缩小到“能否让 NPU 先找出重要的 Token，CPU/GPU 只对关键部分精确处理”。图中① NPU 用 INT8 的 Q·K 粗估重要性，输出每个 Token 的估分；② CPU/GPU 做 Top-k（取重要性排名前 k 的项）得到待精算位置；③ CPU/GPU 对选中位置做稀疏高精度 Attention，输出最终需要的高精度结果。三个箭头是数据依赖，不能把它理解为“所有 Token 在 CPU 上做完整 Attention”，也不能说后续高精度计算全部发生在 NPU。

图下的两个技术小模块各自服务于上述步骤。Graph Bucketing 为阶段①预先生成若干适用于不同量化比例/形状的 NPU 计算图，运行时匹配当前输入以降低误差及反复建图开销；Head-wise Pipeline 使不同 Attention Head（不同注意力计算组）之间的 NPU 估分和 CPU/GPU 选择、精算尽可能交错，减少等待，但同一 Head 内的依赖顺序不能跳过。

一、页面内容详细讲解

图中间三张卡是 SMEPilot 论文抽象出来的三个**相互独立的优化方法**，不是每次任务必须按 1、2、3 顺序通过的流水线。① 分块并行（tile-level partitioning）：把大 GEMM 矩阵切成小块，让常规 CPU 计算与 SME 矩阵计算的可用资源按条件分担，降低某一类资源等待或负载不均。② 流水重叠：不同 tile 之间存在可重叠的阶段，示意当 SME 做某块的矩阵运算时，CPU 对另一块可执行的 Softmax 做处理，以减少阶段间空档；必须尊重每个 tile 自己的数据依赖。③ 布局复用：权重及 KV cache 需满足 SME 的数据布局与 packing 约束，不应每次算子调用都重新转换；预处理一次、后续多次复用是降低搬运和打包成本的思路。右侧两个向右箭头表达数据准备→复用的方向，并不表示零开销或真实 CPU 硬件信号。

对 CPU 技术工作的含义：短期更应改善 LLVM/SME2 lowering、微内核组合、Attention 分块和数据布局复用，而不能因为存在并行/缓存问题就认定需要 Agent 专用指令。下一页把“CPU 内部协同”扩展到“跨 CPU、GPU、NPU 的 Agent 任务调度”。

右侧 B 才是模型运行阶段的资源选择：Runtime 综合任务阶段、精度、用户前台响应要求、后端支持与当前资源状态，决定本次由 CPU 路径还是适用的 GPU/NPU 软件后端承接。CPU 路径调用左侧提前准备的代码；NPU 路径也要依赖厂商/系统后端支持的具体算子，不是 LLVM 画一条箭头就能直接执行。OS/驱动提供资源占用、任务状态与系统 QoE 等约束，Runtime 负责综合使用这些信息。左右分栏相互配合，但不存在被本页证明的统一跨厂商硬件控制协议。

下方三张责任卡是建议的技术所有权，而不是已指派给某个现实组织的人事安排。CPU/LLVM 团队直接负责 SME2 lowering、ABI 正确性、可复用 packed 布局和快路径微内核；Runtime/NPU 软件团队共同研究支持覆盖率、CPU fallback、阶段放置与同步搬运；OS/Agent 平台考虑前台 QoE、工具操作授权和状态的系统边界。对 CPU 团队最实际的策略是先做好自己能交付的代码和执行性能，再用接口协作解决跨引擎损失，不将所有 Agent 语义都塞入 CPU ISA。下一页把“工具效果”和“计算状态有效性”单独展开。

第二卡“让工具操作可验证”，正式方向为“Agent 工具操作的可信执行”，主要由 Agent/App 与 OS 平台承担：用户请求可能对应有副作用的日历或设置修改，工具返回成功不代表用户最终目标已经完成；工程上应绑定操作对象、核验权限与真实结果并支持受控恢复。CPU 团队可以提供高效可靠运行支撑，但这不是 CPU 指令设计本身。

第三卡“改善跨处理器任务分工”，正式方向为“CPU/GPU/NPU 异构执行与 QoE 优化”，主要由 Runtime/OS 负责，CPU/NPU 软件共同参与：算子回退、同步、带宽争用和前台资源压力会抵消 NPU 单算子优势，应按实际阶段和可用资源进行选择。所谓 QoE（体验质量）除了模型算子时间，还包括用户感受到的任务完成时间、卡顿和功耗影响。

下方三张卡是另外一类**尚待研究的问题**：任务进度里是否有不能靠完整日志重建的有用信息；跨 CPU/NPU 的派生数据是否真存在版本化软件解决不了的物理有效性残余；恢复执行的 CPU cache/TLB 等微状态是否在现有亲和性/共享缓存下仍有新价值。它们都用问句写出，不能称为硬件产品构想。最底部的“持续观察”还包括主动 Agent 低功耗、共享缓存和恢复时序；并明确不把普通优先级、取消和缓存机制改名包装成 Agent 专用指令。下一页会说明这些工作为什么应该分年份、有前后依赖地组织。

这是整套 17 页汇报的结束页。它并非再次罗列研究对象，而是把技术判断转成管理层能够回答的三个讨论问题；同时清楚界定这份公开资料研究**能提供技术方向，不能代表已有的项目审批、预算、人事授权或芯片发布日期**。左侧三问与右侧三条边界应结合阅读。

左侧第1问“哪些技术工作优先推进”：建议优先把 CPU/LLVM 现有 ISA、微内核、布局快速执行路径做好，并同步推进 Agent 工具的授权/真实效果核验与 Runtime/OS 跨处理器协调；要管理层确认的是**三类工程/平台方向的相对技术优先级**，而不是“批准三颗新 CPU 芯片”。对 CPU团队而言第一类最直接；第三类是重点跨部门合作；第二类属于 Agent/App和平台主体，需要 CPU团队提供适用支撑。

第2问“哪些问题需要跨团队协作”：编译器/CPU 负责高效正确的执行代码及 ISA/ABI，Runtime/NPU负责阶段放置、模型后端覆盖及同步，Agent/App与OS负责权限、动作回执核验及前台体验。真正需要讨论的是接口如何交接（输入数据格式、状态版本、任务权限、资源信息、目标结果），以及由哪些现实团队承担；本页没有预设姓名或已获授权的组织架构。

第3问“什么证据出现后重新研究专用硬件”：应要求独立公开手机相关研究先证明优化的软件、现有指令和通用 OS 控制仍有可重复的物理瓶颈，能定位新的状态或电路控制点，并使净收益足以和面积、功耗、验证/兼容风险比较。这里的“重新评估”不是开始 PoC 的既定安排，而是对研究结论何时可以被证据更新设置条件。
