## 第 1 页：Agent 任务如何在不同执行资源间分工？

**展示标题与顶端导语**：完全沿用 v1；管理结论不变。

### 视觉层级与唯一节点表

“LLVM”不是独立处理器，“OS/Runtime”和“应用”不是芯片执行引擎。不要将执行引擎简单画成一条从 CPU 流向 NPU 的流水线。

| 内部 ID | 画面标记 | 类型/层级 | 承担什么 | 注意 |
|---|---|---|---|---|
| P1-A | Agent / App（目标、规划与工具动作） | 应用/Agent 层 | 发起任务，规划与验证 | 用户目标的执行主体 |
| P1-R | Runtime / OS（阶段分工与系统资源） | 调度/系统层 | 阶段分派、资源状态、结果汇总 | 软件控制层，不是处理器 |
| P1-C | CPU（可编程控制与选择性计算） | 执行层、分支 A | 动态控制及适用的轻量/不规则算子 | CPU 上程序仍依赖普通编译链 |
| P1-N | GPU / NPU（适配模型阶段） | 执行层、分支 B（概念性分组） | 高吞吐和后端支持良好的模型计算 | GPU 与 NPU 是不同硬件，此处是版面合组，不能声称同一设备 |
| P1-M | 共享数据与派生状态 | 数据/内存支撑层 | 数据布局、版本与有效性 | 支撑两个执行分支 |
| P1-L | LLVM / MLIR 与 CPU 内核库 | 编译和运行时软件的旁注 | AArch64 lowering、ABI、微内核、packing 选择 | **虚线关联 CPU 路径**；不是运行时 CPU→NPU 分发者 |

### 必须实现的边表

| 边 ID | 起点 | 终点 | 标签 | 边的意义 |
|---|---|---|---|---|
| P1-E1 | P1-A | P1-R | 任务请求 / 目标约束 | Agent 向系统发起执行 |
| P1-E2 | P1-R | P1-C | CPU 阶段执行分派 | 将适用工作分派 CPU |
| P1-E3 | P1-R | P1-N | GPU/NPU 阶段执行分派 | 将适用工作分派加速器 |
| P1-E4 | P1-C | P1-R | CPU 完成 / 错误 / 资源反馈 | 执行结果返回 Runtime |
| P1-E5 | P1-N | P1-R | GPU/NPU 完成 / 错误 / 资源反馈 | 执行结果返回 Runtime |
| P1-E6 | P1-C | P1-M | CPU 数据读写 / 版本访问 | CPU 使用共享数据 |
| P1-E7 | P1-M | P1-C | 数据可用 / 有效性结果 | 状态提供和版本验证 |
| P1-E8 | P1-N | P1-M | 加速器数据读写 / 版本访问 | GPU/NPU 使用共享数据 |
| P1-E9 | P1-M | P1-N | 数据可用 / 有效性结果 | 状态提供和版本验证 |
| P1-E10 | P1-L | P1-C | 编译/内核能力支撑（虚线） | 说明 CPU 技术栈，不代表运行时调度 |
| P1-E11 | P1-R | P1-A | 任务状态 / 完成情况 | Agent 根据效果记录决定后续动作 |

**删去**此前模糊的“CPU ↔ GPU/NPU 直接数据交接”作为默认固定箭头：可能通过共享内存/同步路径交接，具体由 Runtime、驱动和接口实现，未有单一标准直接链路。可在 P1-M 附注“跨引擎共享/同步成本”，而不是擅自画直接物理通道。

**版面**：P1-A 顶层 → P1-R 中层 → P1-C/P1-N 同一水平行并行分支 → P1-M 底部；P1-L 与 P1-C 邻接，虚线联系。结果反馈线位于侧面独立通道，不能与任务发放线重合。右侧 1/2/3 管理建议按 v1 展示。每条边的几何方向必须由上表决定，不能按美术偏好倒置。

## 第 2 页：六阶段“时间轴”与五个“责任泳道”严格分开

**展示标题与导语**：沿用 v1，场景标签“概念示意，非论文/设备真实 trace”。

### 泳道注册

| 泳道 ID | 画面名称 | 边界 |
|---|---|---|
| P2-A | Agent / App | 目标理解、计划、结果验证 |
| P2-R | Runtime / OS | 阶段安排、授权约束、状态恢复 |
| P2-C | CPU | 处理动态控制与适用短计算；并不是单独管理 NPU |
| P2-N | GPU / NPU | 可选的适用推理算子 |
| P2-T | 外部工具 / 应用 | 日历等系统 API 的执行和可查询状态 |

**时间列（不是节点 ID）**：S1 理解请求，S2 规划任务，S3 选择并执行适用推理阶段，S4 写入前确认目标/授权，S5 执行工具动作，S6 验证真实效果与后续处理。S3 的“选择执行路径”不应让人以为选择完就已经完成推理，因此补充实际执行子动作。

### 可画的最小节点集合

| 节点 | 所属泳道 | 所属时间列 | 文字 |
|---|---|---|---|
| P2-A1 | P2-A | S1 | 识别用户目标与约束 |
| P2-A2 | P2-A | S2 | 拆解检索/推理/工具步骤 |
| P2-R3 | P2-R | S3 | 按阶段特征选择执行路径 |
| P2-C3 | P2-C | S3 | CPU 执行必要控制/适用算子 |
| P2-N3 | P2-N | S3 | GPU/NPU 执行适用模型算子（可选） |
| P2-A4 | P2-A | S4 | 指定待写对象与动作，必要时请求确认 |
| P2-R4 | P2-R | S4 | 重新检查权限与当前上下文 |
| P2-T5 | P2-T | S5 | 日历工具执行写入并返回调用结果 |
| P2-A6 | P2-A | S6 | 查询/核验用户目标是否真正达成 |
| P2-R6 | P2-R | S6 | 版本失效、停止旧工作及恢复控制 |
| P2-Z | P2-A | S6 | 目标已完成（终态） |

不在每个时间列机械填满五行。P2-C3 与 P2-N3 是视执行内容可选的并行/替代路径，不代表任务固定同时执行二者；在图中使用旁路标注“适用时选择”。

### 连线与触发表

| 边 | 起点 | 终点 | 显示条件/标签 |
|---|---|---|---|
| P2-E1 | P2-A1 | P2-A2 | 目标已解析 |
| P2-E2 | P2-A2 | P2-R3 | 规划需要模型/计算阶段 |
| P2-E3 | P2-R3 | P2-C3 | CPU 适配 |
| P2-E4 | P2-R3 | P2-N3 | GPU/NPU 适配（可选） |
| P2-E5 | P2-C3 | P2-A4 | 必要计算结果返回计划 |
| P2-E6 | P2-N3 | P2-A4 | 加速器计算结果返回计划 |
| P2-E7 | P2-A4 | P2-R4 | 明确对象与操作；需要的确认已获得 |
| P2-E8 | P2-R4 | P2-T5 | 权限/上下文核对通过 |
| P2-E9 | P2-T5 | P2-A6 | 工具调用回执；**尚未证明目标完成** |
| P2-E10 | P2-A6 | P2-Z | 查询效果证据符合目标（成功） |
| P2-E11 | P2-A6 | P2-A2 | 结果不符 → 重新规划；禁止盲目重复有副作用的写入 |
| P2-E12 | P2-R4 | P2-R6 | 失权 / 目标变更 → 不执行写入 |
| P2-E13 | P2-R6 | P2-A2 | 复核权限/版本后需要重规划 |
| P2-E14 | P2-A6 | P2-R6 | 目标变更 / 旧缓存或结果无效 |
| P2-E15 | P2-R6 | P2-Z | 无须继续或取消任务（终态需注明“已取消”，非“已完成”） |

**对 v1 的明确纠错**：不得将 “验证失败→规划” 与 “发生中断→恢复” 绘成同一种无标签回环；后者也可能安全终止。P2-E15 的终态标签必须按分支标成“取消/终止”，不与 P2-E10 的“完成”共用同一结果语义。正式图建议拆成“已完成”和“已取消”两个终态外观节点。

**交互边界**：S4 请求用户确认并非所有动作必需，须写“按权限/风险需要”；R4 负责本页抽象中的授权状态复核，不能宣称真实平台所有 API 都已有该保障。S6 真实效果查询需要可观察证据，不是只看工具返回 status code。

**版面**：主阅读路径按 S1→S6 横向；泳道纵向只用于职责定位；失败回环走上边缘，目标变更/中断走下边缘，防止箭头穿越无关节点。正式制图若空间不足，应以六阶段横向主流程为主体、下方五责任层局部调用图为辅，不能密布 5×6 个未解释的小方块。

## 第 3 页：成本拆分与完整“候选路径比较”，不做伪判定树

### 成本说明（沿用 v1 标题）

`T_stage ≈ T_prepare + T_layout/quant + T_compute + T_transfer/sync + T_fallback` **只作系统成本项目清单示意**。精确定义的墙钟时间受并行、流水、缓存复用和不同模型阶段依赖影响；未经 trace，不能把相加的每一项解释为互斥测量项。更准确的辅助句为：**端到端关键路径时间由依赖和可重叠程度决定，不等于把每项独立测得的时间简单相加。**

### 三列四行表

沿用 v1 四行“工作负载特征 → 可能显著成本 → 执行放置含义”。应当作为**静态对照表**，禁止在行与行之间连向下箭头；表内每行只从左到右解读。

### 决策图（新增显式分支）

目的标题：**为缩短同一任务的实际完成时间，如何选择 CPU、NPU 或混合路径？**

| ID | 节点 | 是/否去向 |
|---|---|---|
| P3-D0 | 固定同一模型/精度/设备/软件版本及 QoE 约束 | → P3-D1 |
| P3-D1 | NPU 后端能高效支持当前算子/形状/精度？ | 是→ P3-D2；否→ P3-D1b |
| P3-D1b | 可否经图重写/优化 NPU 解决？ | 是→ P3-D2；否→ P3-D3（只比较可行 CPU/GPU 路径） |
| P3-D2 | 计算 NPU 路径的准备/数据变换/同步/回退及可复用性 | → P3-D3 |
| P3-D3 | 为所有可行路径建立完整阶段成本候选（CPU/NPU/混合） | → P3-D4 |
| P3-D4 | 同条件端到端总成本和前台 QoE 比较 | → P3-D5 |
| P3-D5 | 选择满足功能、能耗/QoE 约束且总成本最低的路径 | 终态；不得在没有数据时画出具体赢家 |

**修正说明**：旧四步骤列表没有真正条件分叉。“NPU 不支持”也不应直接判定永久用 CPU，因为优化后端/图重写可能改变可行性。CPU/GPU 路径仍需满足模型精度/功能约束。这张图表达**选路方法**，不是当前任何具体设备的测量结果。

## 必须自动或人工复核的验收条款

1. **闭合引用**：所有边的起点终点都在本页节点表中，且每个节点在图中出现一次；判断框的每个分支都有出口。
2. **类型和层级**：编译器、Runtime、执行处理器、共享状态、外部应用不能因视觉便利合并成错误硬件对象。
3. **分支语义**：成功、失败重试、取消终态不可混用；模型/算子是否由 NPU 执行不能在概念图中伪装成固定事实。
4. **画面阅读**：Page1 纵向层级+并行分支，Page2 横向阶段+泳道，Page3 表格逐行横向+完整决策 DAG。必须显著注明“示意/非实测”。
5. **文案/链接**：从 v1 合同保留锁定标题、三页页脚结论和原始参考 URL，并设置 PPT 内真实可点击链接。
