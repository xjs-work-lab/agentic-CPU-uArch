# PAPER-128 — Ripple: Deadline-Aware CPU–GPU Sharing for Embodied Inference

- **Primary source:** https://arxiv.org/abs/2611.01067
- **Full text:** https://arxiv.org/html/2611.01067
- **Submitted:** 2026-10-31 (arXiv preprint)
- **Authors:** Jiadong Zhang, Xiaosong Ma
- **Affiliation:** MBZUAI
- **Target:** ASUS Ascent GX10 / NVIDIA DGX Spark, GB10 UMA platform
- **Review date:** 2026-11-09
- **Status:** FULL_TEXT_REVIEWED / POST_OCTOBER_PREPRINT / ADJACENT_EDGE_UMA_NOT_PHONE
- **Decision relevance:** C (adjacent system scheduling); CG-06 (CPU feedback and Arm host coordination, indirect); not direct mobile NPU or CPU-uArch evidence.

## Q1 — Problem

DGX Spark's GB10 shares LPDDR5X DRAM between a 20-core Arm CPU and a 48-SM Blackwell GPU. GPU LLM/VLM traffic can delay deadline-sensitive CPU perception/control tasks. The paper argues that CPU and GPU resource control is asymmetric: GPU memory volume can be profiled from model layers, while CPU job completion/deadline feedback can reveal interference without a memory-bandwidth counter.

This is an embodied/edge UMA system, not a smartphone. The authors explicitly distinguish its contention topology from phone SoCs targeted by SERENO.

## Q2 — Mechanism

Ripple combines:
1. Layer-/unit-level GPU inference decomposition into pausable grants.
2. Per-CPU-job deadline slack converted into a GPU memory-byte allowance.
3. An online interference model, approximately CPU completion time = baseline duration + (delay-per-GPU-byte × charged GPU volume) + residual.
4. Admission of the longest GPU grant that fits the minimum remaining budget of all active protected CPU jobs.
5. Dynamic GPU SM narrowing for bandwidth-bound LLM decode (typically 8 or 16 of 48 SMs); prefill and VLM compute-heavy work retain full width.
6. SGLang engine hooks and a separate scheduler process; the scheduler occupies one GB10 performance core.

Unlike EdgePace, Ripple does not depend on PMU bandwidth counters. It uses model-derived GPU traffic volume and CPU completion feedback.

## Q3 — Experimental setup

- ASUS Ascent GX10 / DGX Spark, GB10: 20 Arm CPU cores (10 Cortex-X925 + 10 Cortex-A725), 48 Blackwell GPU SMs, 128 GB LPDDR5X, rated 273 GB/s.
- Ubuntu 24.04.3, Linux 6.14, NVIDIA driver 580.95.05, CUDA 13.0, SGLang 0.5.12.
- CPU protected tasks: Costmap, KDNN, stereo matching, quadrotor control, ORB feature extraction.
- CPU periods: 100 ms for most tasks; 20 ms for Control.
- GPU workloads: Qwen3-8B / Qwen3-32B-FP8 LLM and Qwen3-VL-8B / Qwen3-VL-30B-A3B-FP8 VLM.
- Four workload mixes. CPU deadline-miss tolerance 2%; every VLM frame must meet its deadline.
- Scope is batch-one, pausable inference on one UMA system.

## Q4 — Direct comparison with SERENO

The paper explicitly evaluates SERENO's Balanced and UI-First policies, alongside SiGAMMA, whole-engine Pause, Cap-x and unmanaged inference. It reports that SERENO's policies frequently violate the 2% CPU deadline-miss target on this DGX Spark workload. Example: for Robotic1 + Qwen3-8B + Qwen3-VL-30B-A3B at 1.5× deadline slack, SERENO UI-First produces 7.25 LLM tokens/s but 66.95% worst CPU DMR; SERENO Balanced produces 9.53 tokens/s but 99.85% DMR. Ripple produces 7.00 tokens/s at 0.78% DMR. At 2.0× slack, Ripple reaches 8.44 tokens/s at 0.08% DMR.

**Crucial transfer boundary:** this is not evidence that SERENO fails on phones. The paper itself explains the topology difference: in a phone SoC, NPU bandwidth yielded to foreground CPU work can largely be absorbed by the CPU; on DGX Spark, CPU cannot absorb all GPU bandwidth and many CPU/GPU workloads have independent deadlines. Ripple is a cross-platform counterexample to treating one scheduling policy as universal, not a head-to-head rebuttal within SERENO's intended phone workload.

## Q5 — Results and overhead

- Ripple is the only evaluated strategy that consistently meets the 2% CPU DMR target and all VLM deadlines across the tested mixes and deadline settings.
- At the example 1.5× setting above, it retains 7.00 LLM tokens/s while satisfying CPU DMR; SiGAMMA has 6.16 tokens/s but 21.50% DMR.
- At 2× slack in the same mix, Ripple reaches 8.44 tokens/s at 0.08% DMR.
- In an injected CPU memory-reader perturbation test, the adaptive controller keeps KDNN DMR around 0.6% and 1.0% in two intervals; a non-adaptive variant reaches 60.4% and 67.0%.
- With 2× deadline slack, only about 5% of GPU time is idle due to scheduling gaps. At stricter deadlines, budget-wait time dominates the cost.

These results are workload- and platform-specific; do not transfer the token rates or DMR percentages to phones.

## Q6 — Limits and artifact

- One platform (DGX Spark), no phone or NPU evaluation.
- CPU tasks are robotics/embodied workloads; the LLM is best-effort and VLM has a declared deadline. This differs from GUI Agent action chains and Android foreground apps.
- The paper identifies itself as a proof-of-concept for batch-one pausable inference; long prefill needs finer boundaries and the SM-count/admission tradeoff needs more study.
- It modifies SGLang with engine hooks and a separate scheduler. A public code/artifact repository was not located in this review.
- The paper is a preprint; no peer-reviewed venue or independent replication is established here.

## Q7 — Facts, inferences and non-claims

- **[FACT]** Ripple directly compares against SERENO on DGX Spark and shows that SERENO's phone-oriented control does not meet the paper's CPU DMR targets on this distinct UMA topology.
- **[FACT]** Ripple uses CPU completion feedback plus model-derived GPU byte volumes; it does not require a hardware bandwidth counter.
- **[INFERENCE]** C should model platform topology and deadline structure explicitly. A phone CPU/NPU policy should not be assumed to work unchanged on UMA CPU/GPU edge devices.
- **[INFERENCE]** EdgePace and Ripple independently converge on fine-grained accelerator work admission plus deadline-aware CPU protection, but use different signals and target platforms.
- **[NOT ESTABLISHED]** Ripple's method is directly portable to mobile phone NPU stacks, or its byte-volume model can replace PMU/counter feedback on Qualcomm/MediaTek NPUs.
- **[NOT ESTABLISHED]** Any new CPU ISA or microarchitecture feature is needed.

## Q8 — Decision impact

**C: strengthen as a general heterogeneous scheduling discipline, but preserve platform-specific subcases.** Ripple adds no new direct mobile evidence and should not change the mobile portfolio by itself. It does, however, provide a valuable counterexample against a universal scheduler claim and an explicit independent comparison with SERENO on a different topology.

**CG-06: no direct promotion.** The CPU side provides timing feedback and one core hosts the scheduler, but no CPU kernel/LLVM/uArch optimization is proposed or measured.

**B-residual, A, PT-A, R2: no direct change.**
